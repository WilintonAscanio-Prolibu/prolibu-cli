# Prolibu platform map

## Start here

**For the full object list, read `references/modules.md`.** It lists every standard object in
the public API by module, with its API path and one line on what it is for. Use it to turn a
business request ("register a sale", "set up a support inbox") into the right object.

Answer in the user's language. The object names, paths and field names stay as written.

## Which skill to use

| Topic | Skill |
| --- | --- |
| Web forms, ad lead forms, where submissions go | `prolibu-forms` |
| Notify an external system when records change | `prolibu-webhooks` |
| Link a record to an id or URL in another system (`refId`, `refUrl`) | `prolibu-external-refs` |
| Add fields to an object, or create a Custom Object | `prolibu-custom-fields` |
| Automation: code on record events, on a schedule or on demand | `prolibu-scripts` |
| A custom URL or webhook receiver that runs a script | `prolibu-endpoints` |
| Publish a website, landing page or single-page app | `prolibu-sites` |
| Any other object | This skill: read its schema, then follow the write flow |

## Never through a skill

`Token`, `ServiceCredential`, `User`, `Role`, `AuthenticationRule`, `OauthApp`, `OauthGrant`,
`McpSession` and `SyncConnection` hold keys, access or sign-in rules. Do not create, change,
delete or list them. Tell the user to use the Prolibu app (or ask an admin) and stop. Only
exception: reading `SyncConnection` to check sync coverage, as `prolibu-external-refs` does.

## Core relationships

- **Deal → Contact and Company.** A deal points to one `contact` and one `company`. A contact
  also points to its `company`.
- **Deal → Quote → LineItem.** The quote is not a separate linked record: it lives inside the
  deal, in `proposal.quote`. The quote keeps its lines in `lineItems`; each line is a priced
  copy of a pricebook entry (a product at a price-list price).
- **Deal → ProposalVersion.** Saved versions of a deal's proposal. The deal lists them in
  `proposalVersions`, and each version points back through `dealSource`.
- **Presentation → Contact.** A presentation points to a `contact` and a `layout` template.
  It has no link to a deal.

## Fields every record shares

| Field | Meaning |
| --- | --- |
| `_id` | The record's id, generated by the platform. |
| `createdAt` | When the record was created. Set by the platform. |
| `updatedAt` | When the record was last updated. Set by the platform. |
| `createdBy` | The user who created the record. Set by the platform. |
| `updatedBy` | The user who last updated the record. Set by the platform. |
| `workspace` | The workspace (business unit) the record belongs to. |
| `refId` | The record's id in an external system. See `prolibu-external-refs`. |
| `refUrl` | A link to the record in an external system. See `prolibu-external-refs`. |

Line items inside a quote are not records and do not carry these fields.

## Before creating any object without a dedicated skill

Read its schema from `GET /v2/openapi/specification`; never guess field names. The response is
large, so save it to a temporary file outside the repo and read only the object you need:

```bash
node .claude/skills/_shared/prolibu-api.js <your-domain> GET /v2/openapi/specification \
  > "${TMPDIR:-/tmp}/openapi.json"
```

The create fields are under
`body.paths["/v2/<path>/"].post.requestBody.content["application/json"].schema.properties`,
where `<path>` is the API path from `references/modules.md` (for example `deal`). Nested fields
appear with dotted names, such as `proposal.quote`. The spec also lists the account's own
Custom Objects. Schemas of fields named like secrets (`password`, `token`…) print as `***`.
If the path is not in the spec, the object does not exist on that account: say so and stop.

## Writing to an account

Every read and write goes through the helper and the six steps in
[`../_shared/WRITE-FLOW.md`](../_shared/WRITE-FLOW.md): domain, reads only, plain-language
summary, explicit confirmation, write, read back. Read that file before the first write.
